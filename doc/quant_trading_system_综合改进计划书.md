## 一、核心诊断（去重后的共识 + 互补发现）

两份分析在"工程化不足"上完全一致，但 Grok 因为读了实际代码，发现了一个 Claude 单靠 README 看不出来的关键问题，予以最高优先级采纳：

> **双产品定位模糊**：仓库同时装着「事件驱动量化框架」（core/strategy/backtest/risk/execution）和「A股个人持仓助手」（`stock_analysis` + 通知/调度/`trade_monitor`），但 README 只讲了前者。这会让外部贡献者和你自己后续维护时都不清楚"改一个模块会不会影响另一个"。

以下问题按两份计划取交集/互补后重新排序：

| # | 问题 | 来源 | 严重度 |
|---|------|------|--------|
| 1 | 无 tests / 无 CI / 无 LICENSE / 无 pyproject.toml | 两份一致 | 🔴 阻塞级 |
| 2 | 框架与个人助手边界不清，文档未拆分 | Grok 独有，采纳 | 🔴 高 |
| 3 | A股规则缺失：T+1、涨跌停、100股整数倍、成交量约束 | Grok 独有，采纳（比"撮合模型待复核"更具体） | 🔴 高（直接影响回测结果真实性） |
| 4 | 实盘骨架空（CTP/IBKR/Binance 仅 `NotImplementedError`） | 两份一致 | 🟡 中（视是否要实盘） |
| 5 | 单策略风控完备，但**缺跨策略组合层风控**（多策略同标的仓位叠加） | Claude 独有，采纳 | 🟡 中 |
| 6 | 数据质量校验（复权、异常值、限频重试）、多源降级 | 两份一致 | 🟡 中 |
| 7 | 参数寻优 / Walk-Forward 缺失，ML 模块偏 demo | Grok 更具体，采纳 | 🟢 中低 |
| 8 | Dashboard 多个 `*_app.py` 散落，无统一入口 | Grok 独有，采纳 | 🟢 低 |

## 二、改进目标（6 个月路线图，与 v1 保持一致但顺序做了调整）

- **P0（1-3周）**：可安装、可测试、可 CI；框架与个人助手在文档/目录层面拆清楚
- **P1（3-8周）**：回测规则贴近 A股真实交易约束；组合层风控补齐
- **P2（8-14周）**：Paper 交易闭环稳定；一种实盘通道打通（建议 Binance Testnet，接口最简单，用来验证 Live 链路，不代表你要真炒币）
- **P3（持续）**：研究工具（寻优/Walk-Forward）与个人助手打通、Dashboard 统一入口

| 任务 | 验收标准 |

### 阶段 1：回测真实性（3-6 周，P0/P1）

| 任务 | 优先级 | 说明 |
|------|--------|------|
| T+1 限制 | P0 | 当日买入标的当日不可卖，`Portfolio` 持仓需区分「可用/在途」 |
| 涨跌停处理 | P0 | 涨跌停时订单不成交或按规则部分成交，而不是直接按收盘价撮合 |
| 100股整数倍 | P0 | 下单数量取整到 lot_size，边界情况（余额不足一手）需明确丢弃或报错 |
| 成交量约束 | P1 | 订单量不超过当根 bar 成交量的可配置比例，避免"一根阴线吃掉全部流动性"的不真实成交 |
| 停牌处理 | P1 | 停牌日跳过撮合，且不能影响持仓估值逻辑出错 |
| 交易日历 | P1 | A股/美股/加密节假日和时区统一处理，跨市场回测时间轴不错位 |
| 参数网格 / Walk-Forward | P1 | `backtest/optimizer.py`：网格搜索 + 滚动窗口训练测试，输出过拟合提示 |
| 基准对比 | P2 | 相对沪深300/中证500超额收益、信息比率 |

### 阶段 2：风控增强（与阶段1可并行，2-3周）

| 任务 | 来源 | 说明 |
|------|------|------|
| **跨策略组合层风控** | Claude 补充 | 多个策略同时对同一标的产生信号时，检查合并后的真实仓位/暴露是否超过组合总限额，而不是每个策略各自独立检查 |
| 单票日内亏损熔断 | Grok | 触发后当日禁止该标的再开仓 |
| 行业/板块暴露上限 | Grok | 依赖行业映射数据，可作为后续因子研究的副产品 |
| 订单频率限制 | Grok | 防止策略 bug 导致的连续无意义下单 |

### 阶段 3：数据层加固（2 周）

- 统一 OHLCV schema：列名、时区、复权标记（qfq/hfq/none）写进 `DataSource` 接口契约
- `DiskCache` 补充失效策略、增量更新、元数据（下载时间/数据源）
- AkShare 失败时的多源降级（Tushare / 本地 parquet）
- 交易日历接口，回测只在真实交易日推进

---

### 阶段 4：执行与实盘路径（4-6 周，视你是否真打算实盘再决定投入）

**原则不变：先 Paper 全链路闭环，再选一种真实通道，不要多头并进。**

| 路径 | 建议 |
|------|------|
| PaperBroker | 接准实时 bar（定时拉 AkShare），完整跑通「信号→风控→成交→持仓更新→通知」，产出真实成交日志 |
| 实盘通道优先级 | Binance Testnet（接口最简单，先验证 Live 链路本身是否可靠）→ CTP Simnow → IBKR Paper |
| Live 引擎必补 | 线程安全事件队列、断线重连、心跳、日切重置、启动时持仓/资金对账、默认「只读/模拟」开关防误下单 |

---

### 阶段 5：个人助手与框架打通（2-3 周）

- `stock_analysis` 的持仓模型字段与 `Portfolio` 对齐，实现"实盘持仓 → 一键跑风险诊断"
- 扫描结果一键生成"待回测 universe"
- 调度器与 `EventEngine` 的运行时关系写文档，避免两套运行时混用出 bug
- `trade_monitor` 做平台抽象（当前 macOS 通知只是其中一个 adapter）
- Dashboard 收敛为「回测 / 持仓 / 个股诊断」三个页签的统一入口，而不是多个 `*_app.py` 散落

## 五、明确不建议做的事

- 同时对接多个实盘券商——骨架保留，完成度 0→1 只选一条打通
- 把事件引擎重写成复杂 actor 模型——当前单线程回测足够，live 场景用线程安全队列即可
- 做大而全的 Web 前后端——现有 Streamlit 对个人项目性价比更高
- 在没有测试护栏之前做大规模目录重构——先补测试，再动刀
