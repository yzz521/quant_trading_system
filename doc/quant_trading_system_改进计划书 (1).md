# `quant_trading_system` 项目分析与改进计划书

> 基于 GitHub 仓库 [yzz521/quant_trading_system](https://github.com/yzz521/quant_trading_system) 的 README 与目录结构分析整理。
> 说明：本次分析基于仓库首页展示的信息（README、目录树、依赖说明），未逐文件审查源码实现细节，具体建议中标注了"需要结合代码复核"的部分，落地前建议再核对一遍实际代码。

## 一、项目现状概览

### 1.1 优点（值得保留和继续发挥）

- **架构设计合理**：事件驱动 + 队列解耦，`DataFeed → Strategy → RiskManager → Broker → Portfolio` 的闭环清晰，回测与实盘共用同一 `EventEngine`，这是量化框架里比较正确的设计范式（避免"回测一套代码、实盘另一套代码"导致的行为不一致）。
- **无前视偏差处理到位**：订单按下一根 bar 开盘价成交（`fill_policy=next_open`），这是很多个人量化项目容易踩的坑，你已经处理了。
- **模块划分职责清楚**：数据、策略、回测、实盘、风控、组合、分析、ML、看板分层，符合关注点分离，便于后续替换任一层而不影响其他层。
- **风控前置**：订单必须经过 `RiskManager`（仓位/暴露/回撤/现金熔断），而不是策略直接下单，这个"策略只管发信号、风控和仓位系统管"的设计是对的，能防止策略里夹带"野生"下单逻辑。
- **开箱即用的离线体验**：`SyntheticDataSource` 让新用户无需申请密钥/无网络也能跑通 demo，对开源项目的第一印象非常重要。
- **多市场 + 多数据源可插拔**：AkShare / yfinance / 合成数据统一到 `DataSource` 抽象接口，扩展新市场的成本较低。
- **文档质量高于同类个人项目**：README 里给了架构图、目录树、快速开始、策略开发指南、风控参数表、实盘对接表，这在个人量化开源项目里已经算认真的了。

### 1.2 从 README 看到的潜在问题

- 目录里看不到 **`tests/`** 目录，也没有看到 CI 徽章（GitHub Actions / codecov 等），说明**测试体系可能是缺失或很薄弱**的一环——对于涉及"真实资金"的项目，这是优先级最高的短板。
- 文件列表中没有看到 **`LICENSE`** 文件（只有"许可与免责"一段文字声明"仅供学习研究"），法律意义上和一个正式的开源许可证（MIT/Apache-2.0 等）是两回事，对 fork/引用/商用边界不明确。
- 没有 `.github/workflows`、`CONTRIBUTING.md`、`CHANGELOG.md`、`docs/` 等社区化/工程化文件，说明目前更像"个人可用"阶段，还没到"开源协作友好"阶段。
- 三个实盘 Broker（CTP / IBKR / Binance）明确标注是"骨架"，`# TODO` + `NotImplementedError`——这符合诚实披露，但意味着"实盘"目前只是接口预留，真正的实盘可靠性（断线重连、订单状态对账、限频、异常恢复）还未验证。
- 只有 `requirements.txt`，没有版本锁定（如 `requirements-lock.txt` / `poetry.lock` / `pyproject.toml`），量化系统对 pandas/numpy 版本变化很敏感，长期看容易出现"别人 clone 下来跑不动"的问题。
- 风控参数（`max_positions`、`max_drawdown` 等）目前看是**静态配置**，没有看到多策略之间的相关性/组合层面风控（比如多个策略同时对同一标的加仓导致实际暴露远超单策略限制）。
- 数据层依赖 AkShare/yfinance 这类免费接口，README 未提及**限频、断线重试、数据校验（复权/停牌/异常值）**的处理策略。
- Streamlit 看板与回测引擎的关系、看板是否支持"多次回测结果对比"、"参数网格搜索"等研究流程，暂时看不出来。

## 二、改进计划（分阶段路线图）

### 阶段一：工程基建补齐（1-2 周，优先级最高）

这一阶段的目标是让项目"可信、可维护"，而不是加新功能。对量化系统来说，没有测试的框架本质上是不能用于实盘的。

| 任务 | 说明 | 建议 |
|---|---|---|
| 补齐单元测试 | 至少覆盖 `core/event.py`、`core/engine.py`、`risk/`、`backtest/broker.py`（撮合逻辑）、`portfolio/`（净值/持仓计算） | 用 `pytest`，先保证"资金/持仓计算不算错"这类核心正确性，比覆盖率数字更重要 |
| 引入 CI | GitHub Actions：push/PR 时跑 `pytest` + `flake8`/`ruff` + `mypy`（可选） | 几十行 yaml 即可，显著提升可信度 |
| 补 LICENSE | 明确选择 MIT / Apache-2.0 / GPL 等 | 直接影响别人是否敢用你的代码 |
| 依赖锁定 | 迁移到 `pyproject.toml` + `uv`/`poetry`，或至少提供 `requirements-lock.txt`（`pip freeze`） | 避免"半年后装不上"的问题 |
| 补充关键模块的类型标注 | 尤其 `core/event.py`、`strategy/base.py` 等公共接口 | 提升可维护性，IDE 补全友好 |

### 阶段二：回测引擎的严谨性加固（2-3 周）

| 任务 | 说明 |
|---|---|
| 撮合与成本模型复核 | 确认滑点、佣金、印花税、最小手续费在极端情况（涨跌停、停牌、st股）下的行为是否有边界处理 |
| 数据质量校验层 | 复权方式切换、停牌补齐/剔除、异常跳空/极端收益率的检测与告警，避免"脏数据喂出好看的回测曲线" |
| 过拟合防护 | 增加 walk-forward / 滚动窗口回测的标准流程封装（`ml/` 里似乎已有部分），并在 `PerformanceReport` 里加入样本外表现对比 |
| 多策略组合层风控 | 在 `RiskManager` 之上增加组合级别的相关性/集中度检查，防止多个策略对同一标的的仓位叠加突破真实风险敞口 |
| 交易日历与时区处理 | 多市场（A股/港股/美股/加密）交易时间、假期、时区差异是否统一处理，避免跨市场回测时间轴错位 |

### 阶段三：实盘链路可靠性（3-4 周，视是否真的要上实盘决定优先级）

| 任务 | 说明 |
|---|---|
| 完成至少一个真实 Broker 的实现 | 建议先做 `PaperBroker` 的完整闭环验证，再挑一个市场（如 Binance，接口相对简单）落地真实对接 |
| 断线重连与状态对账 | 行情/交易连接断开后的自动重连、重连后本地持仓与交易所持仓的对账逻辑 |
| 异常与限频处理 | API 限频、超时重试、幂等下单（防止重复下单）、订单状态机（部分成交/撤单/拒单）的完整覆盖 |
| 日志与审计 | 结构化日志（订单全生命周期可追溯），便于事后复盘和纠纷排查 |
| 告警机制 | 熔断触发、连接异常、异常盈亏波动时的通知（企业微信/Telegram/邮件等） |

### 阶段四：产品化与社区化（持续）

| 任务 | 说明 |
|---|---|
| 完善文档站 | README 已经不错，但可以拆分成 `docs/` + 使用 MkDocs/Docusaurus 独立部署，降低单文件维护成本 |
| 增加示例策略与教程 | 更多 `examples/`，如"从零写一个多因子选股策略"的分步教程 |
| CONTRIBUTING.md | 明确代码风格、PR 流程、测试要求，降低协作门槛 |
| Dashboard 增强 | 支持参数网格搜索可视化、多次回测结果对比、策略组合的联合回测 |
| 性能优化 | 如果未来要跑分钟级/tick级数据，`pandas` 逐行处理的事件循环可能是性能瓶颈，可以评估 `polars`/`numpy` 向量化或 Cython/Rust 扩展关键路径 |

## 三、优先级建议（如果精力有限，按这个顺序做）

1. **测试 + CI + LICENSE**（信任基建，成本低收益高，1-2周内可完成）
2. **回测引擎正确性复核**（尤其撮合、成本、数据质量，这是量化系统的地基，错了后面全白搭）
3. **组合层风控**（多策略并发时的真实风险敞口，容易被忽视但一旦实盘会出大问题）
4. 实盘链路可靠性（**仅在你真的打算实盘时优先**，否则可以放后面，避免把精力消耗在用不上的地方）
5. 文档/社区化（锦上添花，长期做）
